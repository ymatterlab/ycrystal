FR-QE-IBRAV-01: Quantum ESPRESSO input with ibrav other than 0 (post-0.4.0, 21 November 2026)¶

Requested by the user on 21 November 2026: support pw.x inputs with ibrav ≠ 0; first check whether ASE supports them, and if not, whether the code in the local utils/ folder (external code, ignored by Git) can read them. Branch feature/qe-ibrav from main at 1aae367. Run on the Linux Mint laptop (Python 3.12.3, ASE 3.29.0).

Subsequently merged in PR #47 (c2fa44a) on 21 November 2026 after CI passed on Ubuntu, macOS, and Windows. Available from main, after the v0.4.0 tag.

Findings:

  • ASE 3.29.0 (the pinned version) does not read or write ibrav ≠ 0: read_espresso_in raises "ASE does not support ibrav != 0", and no other part of ASE converts ibrav. ASE 3.22.1 had ibrav_to_cell (its wheel from PyPI was inspected); it was later removed.
  • utils/autoph/pw_utils.py::ibrav_to_cell is ASE 3.22.1's function (identical text) with two changes: a fix of its ibrav = 11 row (a typo that made it fail) and an added ibrav = -13. Checked against QE's Modules/latgen.f90: the lattices it has are right; it has no ibrav = 91 and checks no parameters (a missing c gives a flat cell). It is LGPL code from ASE, inside a repository licensed MIT.

Delivered:

  • io/qe_lattice.py, an own implementation from the pw.x input documentation (INPUT_PW) and latgen.f90: IBRAV_LATTICES (all 20 values pw.x accepts), celldm_from_input (celldm(1…6) or A, B, C, cosAB, cosAC, cosBC with pw.x's abc2celldm mapping), ibrav_cell, and LatticeError with pw.x's checks. For ibrav = -13 the axes of QE 6.5 and later.
  • io/readers.py: QE input with ibrav ≠ 0 opens; alat positions use a; a CELL_PARAMETERS card together with ibrav ≠ 0 is refused (as pw.x does); the source record keeps qe_ibrav and qe_celldm. crystal_sg stays unsupported.
  • Fixtures Si_ibrav2.pw.in, MgB2_ibrav4.pw.in, SrTiO3_ibrav1.pw.in, triclinic_ibrav14.pw.in, and qe_ibrav4_no_c.pw.in (still refused, replacing the removed qe_ibrav2.pw.in in the GUI and command-line rejection tests).
  • scripts/check_qe_ibrav.py: compares with pw.x's output in QE's test suite.
  • Documentation: formats, support matrix, limitations, validation (section F), comparison, architecture, API reference, changelog; CI doctests include the module.

QE versions (asked for by the user, documented in docs/guide/qe-lattices.md): QE's release notes and the source of latgen.f90 at 23 tags (4.3.2 to the development branch) were read and the code of each ibrav compared as text. Only ibrav = -13 changed (QE 6.5: v1(old) = −v2, v2(old) = v1; release notes give (x, y, z) → (y, −x, z) for old crystal positions); -9 appeared in 5.0, 91 and -13 in 5.2.0, -3 in 6.2.0. The A, B, C, cos… mapping is as today from 6.3 (6.2.x ignored cosAC for −13); the bohr changed from CODATA 2006 to 2018 in QE 6.6 (Ycrystal keeps ASE's CODATA 2006 value: relative difference below 5e-9). Compiling the old latgen.f90 versions to compare numbers was not permitted in this session (running downloaded code), so the version comparison is by reading only. This also corrected an earlier statement: the current −13 axes start with QE 6.5, not 6.4.1.

Audit of every ibrav (requested by the user, same day; matrix in docs/guide/qe-lattices.md):

  • Committed tests: all 20 lattices against the documented vectors; all 20 through read_structure in both parameter forms (new: 40 tests); lattice geometry for all 20. Tracing the tests showed every statement of io/qe_lattice.py and of the reader's ibrav branch executed (104 of 104; the 7 unexecuted reader lines are older error paths for missing cards and ibrav = 0).
  • pw.x output: scripts/check_qe_ibrav.py --qe-checkout (new option) over a sparse clone of QE's test-suite (development branch): 289 of 289 applicable inputs agreed (17 lattices; A, B, C form for 1, 2, 4, 6, 14); 112 not applicable (no stored pw.x output, structure read from an earlier run, QEHeat trajectory positions); 6 not read for reasons unrelated to ibrav (Fortran 16.D0 masses in ATOMIC_SPECIES in 5, arithmetic in positions in 1; ASE's parser reads neither).

Plain numbers are left exactly as they were. After the fix: 295 of 295 applicable ibrav ≠ 0 inputs agree (the 6 now read and agree, among them QE's own expression test pw_eval/eval_infix.in); QE's 37 applicable ibrav = 0 inputs agree too (a separate check of the same kind), none unreadable. Tests: 31 new in tests/test_readers.py (grammar, precedence, errors, Fortran reals, files).
  • A grep of QE's whole test suite and example folders found no input with ibrav −9, 91, or −13, so no pw.x reference exists for them in QE.
  • Independent code (the utils copy of ASE 3.22.1's function) and the 17-lattice check were rerun: unchanged.

Not verified: ibrav −9, 91, and −13 against a pw.x run (they rest on the documented vectors, and −9 and −13 on the utils cross-check); inputs written for QE 6.4.1 or older with ibrav = -13 and crystal positions open with the current axes (not detected); running the pw.x comparison script on real macOS and Windows machines; opening such a file in the window by hand. CI has passed on Ubuntu, macOS, and Windows.

M5 caveats¶

  • Handles are 2D markers placed outside the projected block and clamped to the view; with a strongly tilted cell a handle can sit far from its face. Directions nearly along the line of sight have no handle until the view is rotated.
  • The view refits after a handle drag (as after numeric changes), so the block stays in the frame.
  • Esc cancels a drag through the window's Select None shortcut; without a focused window the viewport's own key handler does it.
  • Rotation modes and the step angle are navigation settings, not saved in projects and not undoable (camera navigation stays outside the undo stack by design).
  • Styles transfer per-atom settings only for identical element sequences; there is no matching of atoms between different structures.
  • Style files store the source's element sequence (one symbol per atom); for very large structures the file grows accordingly.

Discrepancies documented without changing behavior¶

  • The previous progress wording and draft GUI docstring said rendering returned immediately. In fact render_png queries the renderer version synchronously (up to 15 s) and prepares files before starting QProcess. The render itself is asynchronous. The GUI's renderer check is synchronous.
  • Frozen structure arrays do not make metadata immutable: the constructor retains the metadata dictionary, and replace shallow-copies it. Project is mutable.
  • Direct Structure construction permits occupancy up to 1 + 1e-6, does not reject non-finite coordinates/occupancies, and does not validate pbc length. The CIF reader rejects occupancy below 1 - 1e-3, rather than every value below 1. These existing tolerances/validation limits are now explicit.
  • The renderer self-test converts discovery/render failures to a result, but file preparation, image decoding, and measurement errors may propagate. A preparation failure after creating a job directory can leave partial files. GUI PNG-copy failures can leave a .part file; the GUI still removes the render job.
  • Project metadata sanitization does not recursively sanitize values converted from NumPy; non-finite values can make saving fail. Optional scene/environment/output sections default on load; missing required structure entries fail. The old M1 evidence wording “missing sections” was too broad and is clarified above.
  • core.compare.supercell is a comparison helper and accepts non-singular integer transforms, including orientation reversal; it is not a GUI supercell feature. Structure comparison wraps fractional differences component by component, rather than performing a general minimum-image search in skewed cells.

Architecture decisions¶

  • System Python, not Miniconda. With Miniconda's interpreter, its bundled libstdc++ (GLIBCXX ≤ 3.4.29) is loaded before the system one, and Mesa 25 cannot initialise GLX: the VTK window crashed.
  • PySide6-Essentials only (no Addons/WebEngine). QT_API=pyside6 is forced before PyVistaQt/QtPy are imported.
  • Ycrystal's own POV-Ray writer from M0. ASE's exporter frames the image itself and writes camera-frame coordinates, so it cannot reproduce an arbitrary panned, non-square view. ASE remains the structure library; its exporter is a reference only.
  • Camera export: explicit location/direction/right/up vectors for an orthographic camera (no look_at, sky or angle), so POV-Ray does not re-derive the basis or change handedness. World coordinates stay right-handed in Å. #version 3.7;, no include files.
  • Colours: written as sRGB through a small macro and converted to linear light (assumed_gamma 1.0, PNG File_Gamma=sRGB).
  • Shared geometry: core.scene.build_geometry resolves atoms (stable IDs (source_atom, image)), radii, colours and cell edges once; the VTK viewport and the POV writer both consume it. Atoms are drawn with vtkGlyph3DMapper (instancing); cell edges are tubes with the same radius as the POV cylinders and cast no shadows.
  • Render jobs: per-job temporary directory, ASCII names, POV-Ray run with cwd = job directory and every output option in the job .ini (user povray.ini defaults such as Display=On cannot interfere). The PNG is then copied to the user's path. GUI renders use QProcess.
  • Renderer discovery: GUI setting → $YCRYSTAL_POVRAY → povray on PATH. --check-renderer / Render ▸ Check Renderer renders a tiny reference scene and verifies sphere positions and colours.
  • Output framing (M0, superseded in M3): M0–M2 rendered the viewport's aspect ratio. Since M3 the output size is explicit and the GUI shows the output frame.
  • Keys: VTK/PyVista default keys (e.g. q closes, w wireframe) are disabled in the viewport; application shortcuts (F = Fit, Ctrl+R = Render, Delete = hide, Esc = select none, Ctrl+Z / Ctrl+Shift+Z = undo/redo) live on the window.
  • Boundary policy: along periodic axes atoms are wrapped into the cell (fractional tolerance 1e-3) and images on faces/edges/corners are added. A displayed atom's ID is (source atom, image offset) with position = input + offset @ cell, so IDs are stable when display settings change.
  • Hiding is presentation state: SceneSettings.hidden holds displayed-atom IDs; hidden balls are absent from the shared geometry, hence from the view and POV export. The structure is never modified (atom deletion/editing remains a later, separate feature).
  • Picking uses an analytic ray–sphere intersection with the shared camera model (core/picking.py), not VTK pickers; a click is a left press/release that moves at most 3 px. The selection highlight is a translucent shell drawn only in the live view.
  • Undo/redo: QUndoStack with one command type that swaps SceneSettings; commands with the same merge key (bond tolerance, bond radius) merge when consecutive.
  • Supercells (M2): repetitions live in SceneSettings and are always expanded from the original structure; boundary images are added on the faces of the repeated block. Image offsets stay relative to input positions, so IDs, selection, and hidden atoms are stable across repetition changes.
  • Bonds (M2): core/bonds.py searches the original cell once with ASE's neighbour list (any cell shape) and stores (i, j, integer shift) without reverse duplicates; build_geometry maps them onto displayed images and gives both renderers explicit endpoint index pairs. Rule and per-pair overrides are in BondSettings.
  • Live-view level of detail (M2): sphere/bond tessellation drops at 2,000 and 8,000 displayed atoms; bonds use the same GPU instancing (vtkGlyph3DMapper) as atoms.
  • Scene panel (M2): gui/panels/scene_panel.py emits requests only; the window turns them into undoable commands and syncs the panel with signals blocked.
  • Import (M1): ASE parses; io/readers.py adds detection, provenance (path, name, format, SHA-256, size, time, reader version, block, element mapping), and checks. Questions (format, data block, element mapping) are exceptions that the GUI answers and retries, so the readers stay GUI-free. Ycrystal's QE reader is assembled from ASE's card parsers because ASE's read_espresso_in ignores A (it looks up an upper-case key in a lower-cased namelist) and resolves labels permissively.
  • Comparison: core/compare.py compares lattice matrices directly and matches atoms by element and fractional position modulo lattice translations.
  • Projects: io/project.py, JSON schema 2 (schema 1 remains readable), written atomically; numbers are canonical, symbols are stored for readability and checked on load. Machine-specific settings (POV-Ray path, last directory) stay in QSettings, not in projects.

  • Camera notifications: the viewport now listens to the VTK camera's ModifiedEvent; the M0 observer on the interactor never fired because VTK raises EndInteractionEvent on the interactor style.

  • Output camera (M3): the GUI keeps VTK's camera for the whole view and derives the output camera (same pose, parallel scale × frame/height ratio). Export, preview, render, and projects use the output camera with the explicit output size; a render start observer keeps it fixed across window resizes.

  • Presets (M3): ycrystal.presets loads JSON manifests (declaration kind, finish, filter, interior, includes, live approximation, provenance) shipped as package data. Scenes store ids; the POV writer writes a texture or a full material per element; the viewport applies the live approximation. Background presets also set a visible cell-edge colour, changed together with the environment in one undo step.
  • Material assignment (M4): SceneSettings stores a default material plus sorted element and displayed-atom overrides and element colours; build_geometry resolves one material and colour per atom. The POV writer declares each material once per element colour (once overall for own-pigment materials) and applies unit-space textures to a scaled unit sphere. The viewport draws one actor per material.
  • Environment model (M4): Environment holds background (solid, gradient, sky), floor, lighting values, and the reflection panel; presets initialise it, the panel edits fields. Gradients and skies use a self-lit backdrop aligned with the frame (a sky_sphere would be one colour under orthographic projection) inside an empty light_group; the floor is tilted 20° towards the viewer; area lights have no jitter so renders are deterministic.
  • Lighting rig (FR-LIGHT-01): lights are values relative to the output camera (origin F, screen basis) resolved on demand by ycrystal.core.lighting; the POV writer, the live view's two scene lights, and the Lighting Setup overview consume the same rig, and no resolved positions are stored.
  • Undo model (M5): one command type carries scene settings plus optional environment and output size; handle drags, style imports, and size changes are single steps; merge keys combine spin-box edits. Camera navigation stays outside undo.
  • Styles (M5): the presentation part of the project format plus the source's element sequence; a pure apply_style returns new settings and user notes.
  • Handles and axis rotation (M5): the viewport's input filter routes handle drags and axis-mode drags away from VTK's trackball; handles are 2D overlays recomputed before each render; repetitions are applied once on release.
  • Thumbnails (M4): genuine POV-Ray renders of fixed scenes, shipped as package data, with scene digests to detect stale images.
  • Render lifecycle (M3): RenderProcess (progress, cancellation, elapsed time, completion state) and RenderQueue (one process, newest request wins, job directory removed after the result slots). The window tags previews with scene_revision and discards stale results; final renders use a separate process with Cancel.
