Readers, projects, and styles¶

See the user-facing format restrictions before importing data.

readers ¶

Read POSCAR/CONTCAR, CIF, and Quantum ESPRESSO pw.x input into a Structure.

ASE does the parsing; this module adds format detection, provenance, and the checks that keep Ycrystal from drawing something different from what the file means:

  • VASP 4 files (no element line) need an explicit element mapping. ASE would guess elements from words in the free-text comment line, which can be silently wrong.
  • CIF sites with partial occupancy, or distinct sites at the same position, are rejected instead of being drawn as an ordered structure.
  • QE input with ibrav = 0 needs a CELL_PARAMETERS card. Other ibrav values (ASE does not read them) are converted here with pw.x's own conventions (ycrystal.io.qe_lattice); crystal_sg positions are rejected. Card values that pw.x reads but ASE does not are rewritten first: Fortran reals such as 16.D0, and arithmetic in coordinates such as 1/4. Species labels are kept separately from elements; labels that do not name an element unambiguously need a mapping.

Interactive questions are raised as exceptions (FormatChoiceRequired, BlockChoiceRequired, ElementMappingRequired) so that the GUI can ask and call again with the answer. The readers never modify the input file and never open a window.

All readers return Cartesian positions in Å with periodic boundary conditions along a, b, and c. POSCAR and QE cells keep the lattice vectors as written in the file (converted to Å); CIF cells are built from the cell parameters with a along x and b in the xy plane.

read_structure ¶

read_structure(path: str | Path, fmt: str | None = None, *, block: str | None = None, element_map: dict[str, str] | None = None) -> Structure

Read a POSCAR/CONTCAR, CIF, or Quantum ESPRESSO input file.

Parameters:

  • path (str | Path) –

    Structure file. It is read once as bytes and never modified.

  • fmt (str | None, default: None ) –

    "poscar", "cif", or "qe" to skip detection; None detects the format with detect_format.

  • block (str | None, default: None ) –

    CIF data block to read; required when a CIF file contains several structures.

  • element_map (dict[str, str] | None, default: None ) –

    Element symbol for each species key of an earlier ElementMappingRequired.

Returns:

  • Structure –

    The structure in Cartesian Å, periodic along a, b, and c. Its metadata["source"] holds the provenance: path (absolute), name, format, sha256 and size_bytes of the file, imported_at (UTC, ISO 8601), reader (the ASE version), and element_map if one was given. Format-specific entries are comment and vasp_version (POSCAR), block and, if known, spacegroup (CIF), qe_species (QE label to element), and qe_ibrav and qe_celldm (QE input with ibrav other than 0).

Raises:

  • FormatChoiceRequired –

    If fmt is None and the format cannot be detected.

  • BlockChoiceRequired –

    If a CIF file has several structures and block is None.

  • ElementMappingRequired –

    If elements are needed for VASP 4 species or ambiguous QE labels.

  • UnsupportedStructureError –

    If the file uses a construct that Ycrystal does not draw (see the module description).

  • StructureImportError –

    If the file cannot be read, is a project file, is malformed, or contains no atoms. str(error) explains the problem.

Examples:

Paths are relative to a source checkout:

>>> from ycrystal.io.readers import read_structure
>>> mgb2 = read_structure("tests/fixtures/MgB2.cif")
>>> mgb2.composition(), mgb2.labels
('MgB2', ('Mg1', 'B1', 'B1'))
>>> mgb2.metadata["source"]["spacegroup"]
{'number': 191, 'symbol': 'P 6/m m m'}

evaluate_qe_expression ¶

evaluate_qe_expression(expression: str) -> float

Evaluate a coordinate of ATOMIC_POSITIONS as pw.x does.

pw.x accepts simple arithmetic for each coordinate (its eval_infix): numbers (also .5 and exponents with e, E, d, or D), +, -, *, /, ^ (power), and parentheses, without spaces. ^ and the signs + and - bind tightest and group from the right (-2^2 is −4, 2^3^2 is 512, and 2^-1 is 0.5); then * and /; then + and -, which group from the left.

Raises:

  • ValueError –

    For anything else, an unbalanced parenthesis, or a division by zero.

Examples:

>>> from ycrystal.io.readers import evaluate_qe_expression
>>> evaluate_qe_expression("1/4"), evaluate_qe_expression("2*(1/8)")
(0.25, 0.25)
>>> evaluate_qe_expression("1/(2/(1/2))"), evaluate_qe_expression("-2^2")
(0.25, -4.0)
>>> evaluate_qe_expression("0.5d0")
0.5

fortran_real ¶

fortran_real(token: str) -> str

Return a Fortran real with a D exponent in the E notation Python reads.

pw.x reads masses and cell vectors with Fortran, which accepts 16.D0 or 1.5d-3; other text is returned unchanged.

Examples:

>>> from ycrystal.io.readers import fortran_real
>>> fortran_real("16.D0"), fortran_real("-1.5d-3"), fortran_real("Si.pbe-d.UPF")

Quantum ESPRESSO lattices (ibrav)¶

qe_lattice ¶

Bravais lattices of Quantum ESPRESSO input with ibrav other than 0 (FR-QE-IBRAV-01).

In a pw.x input, ibrav names a Bravais lattice and its parameters are given either as celldm(1) … celldm(6) (celldm(1) = a in bohr, the others ratios and cosines) or as A, B, C, cosAB, cosAC, cosBC (lengths in Å). pw.x builds the lattice vectors from them with fixed conventions; this module builds the same vectors, so that a structure opens with exactly the cell pw.x uses.

The vectors follow the definitions in the pw.x input documentation (INPUT_PW, the ibrav variable) and pw.x's lattice generator (Modules/latgen.f90), including its checks of the parameters, and the mapping of A, B, C, cosAB… onto celldm (abc2celldm). Every ibrav value pw.x accepts is supported:

========== ========================================================= ibrav Lattice ========== ========================================================= 1 cubic P (sc) 2 cubic F (fcc) 3, -3 cubic I (bcc); -3 is the more symmetric axis choice 4 hexagonal and trigonal P 5, -5 trigonal R, threefold axis along z (5) or along (111) (-5) 6 tetragonal P (st) 7 tetragonal I (bct) 8 orthorhombic P 9, -9 orthorhombic base-centred, C type (two axis choices) 91 orthorhombic one-face base-centred, A type 10 orthorhombic face-centred 11 orthorhombic body-centred 12, -12 monoclinic P, unique axis c (12) or b (-12) 13, -13 monoclinic base-centred, unique axis c (13) or b (-13) 14 triclinic ========== =========================================================

The vectors are those of QE 6.5 and later. They are the same in every older version, except for ibrav = -13: QE 5.2.0 to 6.4.1 used other axes, v1(old) = −v2 and v2(old) = v1 (pw.x warns about this change). crystal positions written for the old axes therefore describe other atom places here; QE's release notes convert them with (x, y, z) → (y, −x, z). The mapping of A, B, C, cos… onto celldm is that of QE 6.3 and later (6.2 ignored cosAC for ibrav = -13). Details, and how this was checked, are in the user guide (Quantum ESPRESSO lattices).

Examples:

Silicon in the fcc lattice of pw.x (ibrav = 2, celldm(1) in bohr):

>>> from ycrystal.io.qe_lattice import ibrav_cell
>>> ibrav_cell(2, (10.2631026323, 0, 0, 0, 0, 0), bohr=0.529177).round(4)
array([[-2.7155,  0.    ,  2.7155],
       [ 0.    ,  2.7155,  2.7155],
       [-2.7155,  2.7155,  0.    ]])

MgB2, hexagonal, from crystallographic parameters in Å:

>>> from ycrystal.io.qe_lattice import celldm_from_input
>>> celldm = celldm_from_input(4, {"a": 3.086, "c": 3.524}, bohr=0.529177)
>>> ibrav_cell(4, celldm, bohr=0.529177).round(4)
array([[ 3.086 ,  0.    ,  0.    ],
       [-1.543 ,  2.6726,  0.    ],
       [ 0.    ,  0.    ,  3.524 ]])

project ¶

The .ycrystal project file: versioned JSON with the embedded structure.

A project that uses a background picture is saved as a ZIP package instead: the same JSON document as project.json plus the picture under assets/ (see ycrystal.io.package). Both forms are recognised by content, so the suffix stays .ycrystal.

A project reopens without the original structure file: the canonical structure (cell, positions, elements, labels, occupancy, movable flags) is stored in full, together with its import provenance, the display settings (including hidden atoms), environment, camera, and output settings. Floats are written with Python's shortest round-trip representation, so reopening reproduces every coordinate exactly.

The top-level JSON object has the keys format (always "ycrystal-project"), schema_version, generator, saved_at, structure, scene, environment, camera, and output. Machine-specific settings such as the POV-Ray path are not stored in projects.

Schema history: 1 — first version (M1); 2 — repetitions, cell mode, and bonds (M2); 3 — material and background presets, explicit output size (M3); 4 — element and atom material overrides, element colours, and the full environment: background type, floor, lighting, and reflection panel (M4); 5 — element radii (M5); 6 — background pictures (environment.background.image, ZIP packages with assets; FR-BGIMAGE-01) and custom material variants (top-level materials list with the full definition of every variant the scene uses; FR-MATERIAL-01); 7 — atom-attached vectors (scene.vectors with source defaults and image overrides at full precision, scene.vector_style; FR-VECTOR-01); 8 — the element legend (scene.legend; FR-LEGEND-01), absent and so disabled in older files. Projects without a picture are still single JSON files. Older files open with the M3 appearance: no overrides, plain background, no floor, and the "soft" lighting. Schema-1 files load with bonds disabled to preserve their original appearance. In every schema the saved camera describes the output image of output.width × output.height pixels (schemas 1 and 2 recorded the output size the camera was rendered at), so reopening reproduces the framing exactly, whatever the window size. Schema-1/2 files get the "satin" material they were drawn with, and the "transparent" background preset if their output had a transparent background.

The optional output.aspect_locked and output.aspect_ratio keys store the Render panel's aspect-ratio lock (FR-RENDER-01). They do not change the stored contract, so the schema version stays 5: files without them open locked to their own width / height, and Ycrystal 0.1.0 ignores them.

save_project ¶

Read a project file.

Parameters:

('SrTiO3', True)

Pictures and packages¶

images ¶

Imported pictures: validation, normalisation, and content-addressed storage.

Background pictures (FR-BGIMAGE-01) are imported once and then referred to by content identity: the SHA-256 digest of the stored bytes. Renders, projects, styles, and exports use the stored bytes, never the original path, so moving or deleting the original file changes nothing.

Import rules: PNG and JPEG files are decoded with Pillow to check them. A file is stored unchanged when POV-Ray 3.7 can read it as it is (RGB or greyscale PNG, with or without alpha; RGB or greyscale JPEG) and has normal orientation; otherwise (EXIF rotation, CMYK, palette, or other modes) the decoded, upright pixels are stored as PNG. The size limits are MAX_IMAGE_BYTES, MAX_IMAGE_SIDE, and MAX_IMAGE_PIXELS.

Stored pictures are kept in a process-wide registry (register_image, get_image). Entries are immutable and keyed by their content, so registering the same picture twice is harmless, and undo/redo steps that still refer to a replaced or removed picture keep working for the whole session.

package ¶

ZIP packages for projects and styles that carry pictures (FR-BGIMAGE-01).

A package is a ZIP archive with one JSON document (project.json or style.json, the same document a plain JSON file holds) and the pictures it refers to under assets/, each named by its content identity: assets/<sha256>.png or .jpg. Files without pictures stay plain JSON. Readers recognise the two forms by content (the ZIP signature), not by the file-name suffix.

Reading is defensive: entry names must be relative, without .., backslashes, or drive letters; sizes are limited (see the constants); every referenced picture must be present, decode as a picture in stored form, and match its digest. Anything else is refused with a message, and nothing is changed.

Styles¶

style ¶

Reusable figure styles (.ycstyle files).

A style is the presentation of a project without its structure and camera: materials, colours, radii, display settings, the environment, and the output size. It can be applied to another structure; the structure's scientific data are never changed.

A style whose environment has a background picture is saved as a ZIP package with the picture (style.json plus assets/, see ycrystal.io.package), so it works after the original picture file is moved or deleted; other styles stay plain JSON. Style schema 2 adds the picture record and the definitions of the custom materials the style uses (FR-MATERIAL-01); schema 3 adds the element legend (FR-LEGEND-01). Older styles still load, with the legend disabled.

Transfer rules

A style has four parts; apply_style applies any subset of them (see STYLE_PARTS):

appearance Default material. Material, colour, and radius overrides of elements are applied to the elements the target structure contains; overrides of other elements are left out and listed in the notes. The vector arrow appearance (placement, length mode, sizes, colour, material) and the element legend (FR-LEGEND-01) are applied too; the legend's custom element order follows the element mapping. display Atom size, repetitions, boundary atoms, cell edges, bond settings. Bond-pair rules apply when the target contains both elements. environment Background, floor, lighting, transparency, and the cell-edge colour. output Output image size in pixels.

Vectors themselves (components and atom attachments, FR-VECTOR-01) are a property of one structure, not of a look: styles never store or transfer them, and importing a style keeps the target's vectors unchanged.

Per-atom material overrides and hidden atoms refer to individual atoms of the source structure. They transfer only if the target is compatible: the same number of atoms with the same element at every position in the input order (for example the same structure read from another file or relaxed). Otherwise they are left out, and the notes explain why.

Examples:

>>> from ycrystal.core.samples import perovskite_srtio3, triclinic_marker
>>> from ycrystal.core.scene import Environment, SceneSettings
>>> from ycrystal.io.style import Style, apply_style
>>> source = perovskite_srtio3()
>>> scene = (
...     SceneSettings(material="glossy")
...     .with_element_material("O", "glass")
...     .with_element_material("Ti", "gold")
...     .with_atom_materials([(0, (0, 0, 0))], "chrome")
... )
>>> style = Style.from_state(source, scene, Environment(), (800, 600))
>>> target = triclinic_marker()
>>> sorted(set(target.symbols))
['Cl', 'Fe', 'N', 'O', 'S']
>>> result = apply_style(style, target, SceneSettings(), Environment(), (1200, 800))
>>> result.scene.material, result.scene.element_materials, result.scene.atom_materials
('glossy', (('O', 'glass'),), ())
>>> result.output_size
(800, 600)
>>> print(result.notes[0])
Element overrides for Ti were not applied: the structure has no Ti.
>>> print(result.notes[1][:52])
1 per-atom material override was not applied: it ref

resolve_element_map ¶

resolve_element_map(style: Style, structure: Structure, element_map: dict[str, str | None] | None = None, parts: tuple[str, ...] | list[str] = STYLE_PARTS) -> ElementTransfer

Decide where each of a style's element settings goes in a structure.

Without a mapping every element keeps its symbol: its settings apply if the structure contains it (the transfer rule of earlier versions). A mapping sends the settings of a source element to another element of the structure, or leaves them out (None); the mapping is a presentation choice, not a statement of chemical or crystallographic equivalence.

Parameters:

  • style (Style) –

    Style whose element settings are transferred.

  • structure (Structure) –

    Target structure; it is read, never modified.

  • element_map (dict[str, str | None] | None, default: None ) –

    {source element: target element or None}. Elements that are not keys keep their symbol. {"Ti": "Ti"} is allowed and changes nothing.

  • parts (tuple[str, ...] | list[str], default: STYLE_PARTS ) –

    Parts that will be applied (decides which element settings count).

Returns:

  • ElementTransfer –

Raises:

  • ElementMapError –

    If a key or value is not an element symbol, a target element is not in the structure, two source elements are mapped to the same target, or a mapped element would land on an element that keeps its own settings by symbol. Ambiguity is an error, never resolved by order.

Examples:

>>> from ycrystal.core.samples import perovskite_srtio3
>>> from ycrystal.core.scene import Environment, SceneSettings
>>> source = perovskite_srtio3()
>>> scene = (
...     SceneSettings()
...     .with_element_material("Ti", "gold")
...     .with_element_color("O", (1.0, 0.0, 0.0))
... )
>>> style = Style.from_state(source, scene, Environment(), (800, 600))
>>> resolve_element_map(style, source, {"Ti": None}).targets
(('O', 'O'),)
>>> try:
...     resolve_element_map(style, source, {"Ti": "O"})
... except ElementMapError as error:
...     print(str(error)[:45])
O would receive the settings of both O and Ti
